## 一个客户端不代表一个响应格式

RustGLM 同时接入 Chat Completions、Responses 与 Anthropic-compatible Messages。它们都有“生成回复”这个业务目标，但事件、终止信号、工具调用和错误形态不同。SDK 的工作是保留这些契约，不能为了界面统一就抹平信息。

流式文本也不是按网络 chunk 自然对齐的。事件可能被拆开，多个事件可能同批到达；解析器需要先恢复协议边界，再把完整事件交给业务。连接正常关闭与协议正常结束同样要分别判断。

## 凭据必须由调用者显式拥有

客户端从参数拿到 API Key 或已有 token，不隐式搜索磁盘配置。构造配置不发起请求，持久化也由调用方控制。这样一个测试可以只构造对象而没有外部副作用，服务端也能明确决定凭据的作用域和生命周期。

环境密钥解析是可选工具，不是全局魔法。业务日志应记录请求 ID、端点类别和错误，不应把原始 Authorization 或完整用户上下文当成调试必需品。

## 为什么默认不自动重试 POST

超时可能发生在服务器已经接收请求之后。此时再次发送生成或创建任务请求，可能带来重复成本或重复对象。RustGLM 默认关闭 HTTP 重试；显式开启后，文档将自动重试范围约束到幂等方法。

调用方仍需定义自己的恢复策略。查询一个已有任务的状态，与重新创建任务是两回事；收到部分流式文本后重连，也不能直接把两次生成拼成同一条答案。

## SDK 的预算与业务预算

HTTP 超时、模型输出上限、历史裁剪和用户等待期限解决不同问题。工具调用还可能触发另一轮网络工作，应该纳入同一次业务请求的总预算，而不是每进一层就重新获得无限时间。

Realtime 和 MCP 引入长连接与工具生命周期。断开连接后必须知道哪些请求取消、哪些结果仍可能到达；迟到回调不能覆盖已经切换的会话。

## 如何验证一个接入

先以测试服务覆盖合法事件、分片边界、未知事件、错误帧、提前断连和取消，再对真实账号执行最小请求确认服务权限。测试服务证明客户端协议行为，真实调用确认特定模型与账号条件。

SDK 不保证第三方服务永远可用，也不能从类型存在推导账号获得所有功能。固定版本、实际请求配置与服务端错误共同组成排障记录，任何一项缺失都容易让重试变成碰运气。
