## 密钥在哪里，比算法名字更值得先问

Silovent 把 Kotlin 交互层和 Rust 密钥处理分开。SPU 保存密钥，以不透明句柄提供派生、封装和流式处理能力，JNI 不把 vault key 作为普通 byte array 交给 JVM。这里的 SPU 是仓库的软件抽象，不是手机上新增加的一颗安全芯片。

减少跨语言复制有实际意义：调用方更难无意间把密钥放进日志、状态对象或长寿命缓存。但原生堆在密钥使用期间仍然存在，root 或调试环境的能力不能靠一个类名消失。

## 文件分块解决的是访问粒度

按块认证加密可以在 seek 时只处理所需内容，而不是解密整个视频。每块的 nonce、tag、编号与文件身份需要维持一致约束；整文件校验与块级认证也各有作用。

CRC32 用于检测存储错误，不能代替攻击者面前的认证。读取一个容器时，应先校验头部结构和长度，再逐步建立会话；损坏块不应以“部分成功”的方式悄悄变成可信明文。

## 句柄必须拒绝过期使用

Rust 会话采用 ID 注册表，避免 JNI 把任意整数当原始指针。关闭后再用、重复关闭或把读取句柄交给写入接口，都应明确失败。锁定不仅改变界面，还要销毁密钥与相关会话，阻止旧操作在后台继续读取。

并发导入和播放时尤其需要测试锁定边界：用户按下锁定之后，已经排队的解密任务和迟到回调不能把新的明文重新送回可见界面。

## 生物识别与密码承担不同职责

首次设置密码建立基本解锁路径，Android Keystore 与生物识别可以提供附加的密钥保护。StrongBox 优先不意味着每台设备都有 StrongBox；硬件回退和指纹变更后的失效行为必须明确呈现。

备份恢复也是密码系统的一部分。只有加密文件而没有可恢复的元数据或密钥材料，可能只是把数据永久锁住。评估工具时应先用可丢弃文件走完导入、锁定、重启、导出和恢复。

## 删除不等于物理消除证明

README 描述了胁迫密码触发清理，但在闪存上，覆写和删除受控制器、缓存、快照与磨损均衡影响。不能把文件层操作直接宣传为任何设备都可证明的物理抹除。准确的描述应落到密钥销毁与可访问数据路径。

应用没有网络权限，是可以检查的配置事实；它不能覆盖操作系统备份、已 root 环境或用户主动导出后的数据。本文介绍代码结构与验证方法，不把它改写成绝对隐私承诺。
