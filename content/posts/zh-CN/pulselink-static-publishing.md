## 内容先成为可检查的文件

PulseLink 的文章不是在访问时临时生成。结构化文章与 Markdown 经过构建进入资产目录，Flutter 加载目录后按语言和稳定 ID 建立路由。这样首次阅读不依赖 GitHub API 额度，也不会因为内容接口暂时失败而只剩空卡片。

文章标题会变化，ID 应尽量稳定。URL、项目关联和评论关键词都可以绑定 ID，编辑标题时就不必迁移已有讨论。文章内容与展示组件分离，也让编译期校验能够在页面运行之前发现路径或元数据问题。

## 静态托管仍然可以编辑

浏览器可以调用 GitHub API，但它不能替代 GitHub 的权限系统。发布身份必须来自凭据对应的真实用户响应；填写一个用户名或在本地存储设置“管理员”都不是认证。

站点的发布器核对账号、仓库所有者和写权限，实际提交由 GitHub 执行。令牌只能在内存中使用，不应写入 URL、日志或草稿存储。纯静态产物也没有安全保存 OAuth client secret 的位置。

## 提交成功与上线成功不同

内容提交到仓库后，Actions 仍要执行依赖获取、内容构建、字体准备、检查、测试与 Web 构建。只有部署完成，读者才会拿到新页面。编辑器应报告真实阶段，而不能在收到 commit SHA 时就宣布“全站已上线”。

更新文件要带读取时的 SHA。两个标签页同时编辑时，后一个提交应得到冲突而不是默默覆盖。网络超时又有不同语义：请求可能已经在服务端完成，重试前需要重新读取，避免把没有收到响应误判为没有提交。

## Hash 路由解决了什么

GitHub Pages 不替客户端重写任意页面路径。Hash 路由让语言和文章地址可以直接打开与刷新，但页面依然主要由 Flutter 渲染。它解决访问和客户端定位，并没有自动生成每篇文章独立的预渲染 HTML。

因此不要把深链接可用写成搜索收录已优化。页面 metadata、可访问性和社交抓取各有自己的验证对象，静态壳页面与已运行的 Flutter 应用也可能被不同抓取器看成不同内容。

## 评论属于另一条数据链路

giscus 按需加载，讨论数据保存在 GitHub Discussions。页面需要核对 iframe 消息来源和发送窗口，防止任意窗口伪造高度或配置消息。第三方暂时失败时，应保留直接到 GitHub 讨论的路径。

评论登录和站点发布登录用途不同。一个访客可以被允许评论，并不因此得到文章或友链的管理能力；这类权限必须在每个写入口上分别成立。

## 动画与构建证据

共享动画时钟和局部重绘可以减少重复调度，但真正流畅度仍需浏览器与设备测量。截图用于检查版面，不能用来证明帧率；单元测试用于状态和边界，也不会自动证明所有设备都无问题。

本站文章保留固定来源提交，便于读者复查写作时看到的行为。项目继续更新后，历史分析仍然可追溯；更新内容时应重新核对源码，而不是把旧文章链接机械地换成 main。
